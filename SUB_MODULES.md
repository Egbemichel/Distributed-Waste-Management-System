# DWMS Sub-Module Catalogue

> **The single source of truth for sub-module assignment.**
> Read this file before claiming a branch. If the file and the slides disagree, this file wins.

---

## TL;DR

- **51 features** grouped into **11 groups**.
- **3 roles** per feature: **IMP** (implementer), **TEST** (tester), **DOC** (documenter).
- **51 × 3 = 153 unique modules.**
- **120 are assigned** (one per student). **33 are stretch** — held for fast students, drop-in replacements, and reassignments.
- **Only features in the [ready set](#ready-set-by-week) are claimable today.**
- Every module has **one branch**, **one PR**, **one merge target (`main`)**, **one reviewer**, **one definition of done**.

---

## How to claim a sub-module

1. **Read your group's table below.** Find the features in the group you are assigned to (or the group you want to learn in).
2. **Check the `Week` column.** Only features whose `Week` is ≤ the current teaching week are claimable *right now*. The `Deps` column names the features that must already be merged.
3. **Verify against the ready set.** Open `docs/architecture/ready-set.md`. It is regenerated by CI on every merge to `main`. If your feature is not on it, it is blocked — pick another from the ready set.
4. **Open a Discussion** titled `claim: <feature-id>/<role> by <your-username>` with a 1-paragraph body naming the feature, role, branch, and your first 48-hour deliverable.
5. **Create the branch** using the exact name in the `Branch` column. Push to your fork.
6. **Open a WIP PR** against upstream `main`. Title: `WIP: <branch-name>`. Label: `wip`. This is a placeholder; it makes your work visible to the cohort.
7. **Commit your first artefact within 48 hours**:
   - **IMP**: the OpenAPI spec change for your feature.
   - **TEST**: a failing test asserting the feature's behaviour.
   - **DOC**: the tutorial outline (headings only, no content).

## Legend

### Container type

| Code | Meaning | Where it lives |
|------|---------|----------------|
| **PS** | Pooled Service | Code inside an existing service's container (no new Dockerfile) |
| **DS** | Dedicated Service | New container with its own Dockerfile, port, and healthcheck |
| **MS** | Managed Service | Provider-hosted (PaaS/SaaS) — connection string only |
| **CI** | CI-only | Runs in GitHub Actions; no runtime container |
| **ED** | Edge artefact | Deployed to CDN or static host; no backend |
| **DB** | Database workload | Alembic migration, seed, or scheduled job inside an existing service |

### Deployment

| Code | Meaning |
|------|---------|
| **M** | Multi-replica (≥2), stateless, behind the gateway |
| **M-sticky** | Multi-replica with session affinity (WebSocket) |
| **SG** | Singleton (1 replica, no autoscale) |
| **ST** | Stateful; requires PVC or managed DB |
| **J** | Scheduled job (cron or one-shot) |
| **N/A** | CI or edge; not a runtime deployment |

### Role

| Role | Branch prefix | Merges | Ownership |
|------|---------------|--------|-----------|
| **IMP** | `feat/<obj>/…` | Implementation + OpenAPI spec + unit tests | The code |
| **TEST** | `test/<obj>/…` | Integration, e2e, contract, and edge-case tests | The test suite |
| **DOC** | `docs/<obj>/…` | Tutorial, ADR, docstrings | The documentation |

`<obj>` is `obj1`, `obj2`, `obj3`, or `chore` — matching the three capstone objectives or "no objective."
